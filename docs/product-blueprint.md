# 产品蓝图

## 项目定位与产品价值

个人 AI 助手的长期愿景是模块化、本地优先的个人 AI 工作空间。**v0.2 的近期定位是面向个人 AI 辅助软件开发的项目上下文协同能力**：连接云端规划与本地 Coding 的可信事实，优先为现有 AI 客户端提供本地项目状态和后续变化查询，再渐进扩展项目全景与独立个人知识库。MCP 是首期接入形态，不是业务能力的唯一实现方式。

本项目自身的规划、架构文档与后续代码也是正式项目成果；设计进展不应因尚未编码而显示为“没有项目进展”。

## 业务模块与边界

| 模块 | 核心产品能力 | 当前产品定位 |
| --- | --- | --- |
| 1：项目接入与上下文管理 | 本地目录和 GitHub 仓库独立接入或关联；项目结构/文件/Git 事实查询；已观察版本之间的变化感知 | 近期实施重点，默认只读，不重复建设 Git |
| 2：智能项目管理 | 项目目标、模块与功能全景；设计和开发进展展示；复用任务、审核和 GitHub 证据提供只读汇总与提示 | 重要产品体验，分阶段实现，不接管现有 Agent 验收 |
| 3：个人知识库 | PDF、技术资料、网页与视频链接、笔记收藏；基础分类、检索和 AI 总结 | 相对独立的业务模块，允许可选项目关联 |

**独立工作空间是长期可选界面**：首期优先复用 Codex / DeepSeek Harness 等现有 AI 客户端，不要求自建聊天、模型管理或 Web/桌面工作台；项目事实核心须独立于 MCP 与宿主 UI。

## 模块 1：第一阶段核心体验

- **已完成的首期技术验证（T01）**：Windows Codex 通过本地 MCP 真实调用只读工具，读取固定授权项目的分支、HEAD 与工作区状态，带来源及失败说明；这验证的是接入原型，不代表完整项目注册、持久化或版本变化感知已实现。
- **后续业务目标**：接入一个本地项目或独立 GitHub 仓库，也能够明确关联二者。
- 按需读取项目目录、文件、当前分支、提交与本地工作区状态；远程仓库可在没有本地克隆时查询。
- 打开项目或主动刷新时，以必要的上次成功观察版本标识为比较基线，识别新观察到的提交或其他可查询差异，显示来源、版本、检查时间。
- 不复制完整代码仓库、不保留每次完整扫描快照、不将 GitHub 推送状态与本地未提交修改混为一谈。
- 远端不可用、权限不足、数据过期或变更范围无法确认时清楚提示，不伪造完整历史。

## 云端规划与本地 Coding 的协同场景

- **云端规划**：ChatGPT 项目空间保存讨论与 Human 决策背景；经确认并需长期遵循的设计通过既有 Git/PR 流程写入正式文档，聊天记录不是 Git 仓库的自动同步副本。
- **本地实施**：Codex / DeepSeek Harness 依据已授权范围编码、测试与交付；本地 MCP 按需查询其可访问的真实项目事实。
- **GitHub 共同基线**：已合并 `main` 为正式版本；已推送分支和 PR 为候选版本，不能代表本地未提交工作。云端按需查询实际版本及证据，不将本地未知状态推断为无变化。
- **交接**：任务开始核对本地与远端版本，交付时报告实际 HEAD、PR、验证与云端不可见的本地状态；不默认自动同步，也不共享不同 AI 客户端的聊天记忆。
- **真实使用样例**：在本项目 Windows 工作区 `E:\AI-assistant` 验证本地只读工具；云端使用 GitHub 读取相同项目已共享的版本化设计。

## 模块 2：项目功能全景与进度信息

模块 2 的产品目标是：用户打开项目，能立即理解**项目做什么、有哪些模块和功能、哪些已完成设计、哪些正在开发及其依据**。这不等于要先开发复杂的绘图引擎或另一套任务管理系统。

### 信息层级及来源

- **项目 → 模块 → 功能 → 相关任务/设计与执行证据**；产品功能层级不同于代码文件夹结构。
- 以现有产品蓝图、项目介绍和架构文档描述功能结构，优先复用仓库内 Markdown 任务/审核记录、GitHub Issues/PR 和测试结果说明实际活动。
- 只做能够明确证实的任务与功能关联；来源冲突、未知和旧数据要标记，不依赖标题相似度自动合并。

### 两个进展维度

- **设计进展**：反映需求、架构和功能设计工作，区分讨论/待确认与经过 Human 确认的设计；设计文件是否已提交到 Git 是另外的版本事实。
- **开发进展**：反映功能实现、测试和人工验收；提交代码、PR 合并或测试通过均不能单独等同于已验收。
- 具体状态枚举、阻塞分类与正式完成率算法尚未确定；第一版不得为了好看的百分比推断未知任务或功能已完成。
- 正式任务和验收状态沿用已有权威记录，AI 分析只提出建议；暂不实施重复的 Agent 测试、审核、验收或任务派发体系。

### 可视化策略

- **基础视图**：稳定显示项目介绍、模块/功能卡片、版本变化与详情入口，确保状态可追溯。
- **AI 辅助理解**：利用模型按需从现有文档提取功能结构、解释变化并组织图表描述，重要推断需与事实区分。
- **可选效果图**：根据使用需要通过模型 API 生成较丰富的项目功能/架构视觉效果；静态生成图不作为正式状态唯一来源，也不替代必要交互。
- 视觉效果的具体形式、模型及成本暂不决定，不让生成式展示阻碍模块 1 的基础可靠性。

## 模块 3：个人知识库

独立支持资料收藏、基础分类、搜索和 AI 辅助总结；支持外部引用和用户主动导入的托管资料。网页和视频初期可只保存链接与元数据。与项目关联属于可选协作，不要求先实现项目管理能力。

功能全景是长期重要的**产品体验**，但不是插件首期必须开发的复杂系统。以上分期仅为规划，不自动授予业务实施权限。

## 当前正式范围与未来候选

Bootstrap 已完成，v0.1 已合并，Human 已确认 v0.2 的插件优先与双工作区协同方向。T01/T03 只读接入原型已合并，T02 已完成对 T01 工具的本地 DSH 接入验证。当前下一步是细化模块 1 项目登记与版本变化感知的最小范围；完整模块 1、模块 2 和模块 3 均尚未实现。原型验证证据不等于模块整体验收，后续业务实施仍需明确 Task Scope、验收条件及必要安全/依赖决策。正式项目约束见 [Project Brief](project-brief.md)，架构原则见 [Architecture](architecture.md)。

暂不开发：Coding Agent 直接控制与自动任务派发、复杂多 Agent 协作、多项目高级管理、完整学习/测验/能力评分体系、创意管理、平行的任务状态系统及重复的开发测试/审核/验收引擎。未来是否开发取决于实际需求，不构成排期承诺。
