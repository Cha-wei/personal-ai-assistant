# Architecture

## 目标、状态与约束

本文件记录经 Human 确认的个人 AI 助手总体架构方向，尚不是可运行实现或具体技术选型。项目目标、授权和阶段见 [Project Brief](project-brief.md)，功能分期见[产品蓝图](product-blueprint.md)。设计文件的 Git 版本与 Human 决策、具体任务实施授权须分别识别；本文件本身不授权业务编码。

## 总体架构：本地优先的模块化单体

- **本地优先**：核心业务逻辑和应用业务数据主要在用户本地运行、持久化；GitHub 与云端 AI 为按需访问的外部依赖，不作为基本项目浏览与已有数据查看的前提。
- **模块化单体**：统一工作空间、应用协调与 AI 交互层、业务模块及公共基础能力层组成一个逻辑应用；初期不拆成微服务。
- **职责分离**：统一工作空间提供导航、展示与交互；协调层按需组合模块能力；业务模块管理自己的数据与规则；公共层只承载稳定的跨模块基础能力。
- **渐进扩展**：优先项目接入、Git 事实查询与版本变化感知，再根据真实需求增加 AI 理解、可视化、索引和 Agent 适配，不预先搭建复杂工作流引擎。

界面可以是本地 Web 或桌面应用，具体选择未定；“本地优先”不等于必须具有离线模型推理能力。

## 模块职责和协作边界

### 模块 1：项目接入与上下文管理

- 独立接入**本地项目目录**和**GitHub 仓库**，或将两者显式关联到同一个稳定的逻辑项目；不假定本地与远程状态一致。
- 只读优先，按需浏览目录与文件、查询本地 Git 工作区状态、分支、提交及差异，获取 GitHub 上可访问的仓库信息与历史。
- **版本变化感知是近期核心能力**：在打开项目、主动刷新或后续受控周期检查时，取得当前版本事实，与上次成功观察到的必要标识进行比较；展示变化来源、相关版本和检查时间。同步失败须标识旧信息可能过期。
- 保存必要的项目来源引用、关联关系、最近成功检查的提交/分支标识与时间、连接状态；不默认复制代码仓库、不永久保存每次扫描结果或完整差异、不另建 Git 版本控制体系。
- 已提交的 Git 历史以源系统为准。本地未提交修改可即时查询，但没有独立快照就无法还原两次检查之间的所有编辑过程。
- 按需向 AI 交互层及模块 2 提供带来源、版本与观察时间的事实；**不决定功能是否已完成，也不管理正式任务状态**。

### 模块 2：智能项目管理与项目全景

- 产品方向是让用户一眼理解项目的**目标、模块、功能、设计进展及开发进展**，而不是单纯统计任务数量。
- 首期以**只读项目概览和已有记录汇总**为主：优先复用产品蓝图、架构文档、仓库内 Markdown 任务与审核记录，以及按需查询的 GitHub Issues、PR 和相关验证证据。
- 功能结构以现有项目蓝图为主要来源，按需关联任务与证据；关联不明确时提示待确认，不凭文件夹结构或标题相似度强行合并。
- 区分设计成熟度、开发/验证成熟度及文档的 Git 版本；不因一次提交、PR 合并或测试通过就自动宣称功能已验收。
- Agent 继续按 [Workflow](../CONTRIBUTING.md) 负责开发、测试、自检和审核；模块 2 不重复实现测试/验收引擎、任务派发和第二套正式状态。Human 保留最终验收。
- AI 分析可以提出变化影响与进度建议，但须与原始状态和正式验收记录明确区分。

### 模块 3：个人知识库

- 独立支持 PDF、技术文档、网页/视频链接、笔记的收藏、基础分类、检索和 AI 辅助总结；不以存在项目为前提。
- 用户正式导入的资料可以采用托管副本，现有外部文件及链接可采用引用模式；两者的删除、备份及失效规则不同。
- 与项目或任务的关联是可选能力；知识库不负责代码版本控制或项目正式验收。

### 统一工作空间与公共能力

- 工作台首页、项目基础概览、知识入口和 AI 对话提供统一体验；不重新拥有各模块业务状态。
- 公共基础层仅提供稳定项目身份与来源关联基础、持久化、外部资源权限、模型接入、必要日志与后台任务等能力；各模块自行定义业务规则。
- 模块可以通过清晰接口协作；模块 2 可消费模块 1 的事实，但应能展示尚未关联仓库的规划项目，模块 3 应能独立使用。
- 未来 Coding Agent 适配器优先接收执行事实与证据引用；直接控制 Agent 或复杂多 Agent 编排不在当前范围。

## 数据归属与最小存储

| 类型 | 归属与处理 |
| --- | --- |
| 外部源数据 | 本地代码、远程 GitHub、网页等保留原始归属；默认引用和授权读取，不擅自移动/删除 |
| 应用业务数据 | 项目身份、来源关联、必要配置、用户笔记及确需持久化的记录保存在本地；正式状态以约定的权威记录为准 |
| 托管知识资料 | 用户主动导入的文件可由知识库管理副本，区别于外部引用文件 |
| 衍生数据 | 提取文本、AI 分析、搜索索引、缩略图与缓存应标识来源，能重建的尽量可重建；编辑后正式保存的用户知识不是可随意清除的缓存 |
| 凭证、日志与备份 | GitHub/模型密钥与普通业务数据分离，敏感备份受保护；外部源文件是否纳入备份须明确 |

应用运行数据与应用代码仓库分离。解除项目关联不删除原有代码；归档、解除关联、删除托管资料与清理缓存的语义应区分。迁移时允许重新绑定已移动的项目路径。完整备份、恢复及凭证存放技术尚待设计。

## 项目事实、AI 与可视化边界

1. **事实层**：Git、本地工作区、GitHub、项目文档及实际测试/审核记录提供可追溯信息；明确来源、版本、观察时间和可用性。
2. **AI 理解层**：根据当前目标按需读取最小必要上下文，解释项目结构及版本变化，辅助整理功能结构和可视化描述；其判断是建议，不是原始事实或批准。
3. **表现层**：基础项目概览、版本变化和来源详情必须稳定可用；功能卡片、关系图和丰富的 AI 生成效果图可渐进增强。静态效果图不能替代可交互详情或正式状态数据。

项目或网页内容为不可信数据，不能借内容文本授予工具权限。云端模型调用限制发送范围；默认只读访问项目数据，文件写入、命令执行、Git 推送与正式状态改变需要独立授权。外部服务不可用时，本地已有数据和可查询事实应尽量可用，同时展示远端/AI 能力不可用或信息过期的限制。

## 分阶段实施方向（非本文件授权）

1. 最小本地工作空间与模块 1：项目注册、本地/GitHub 接入、文件和 Git 事实查询。
2. 版本变化感知：必要的观察基线、差异查询、来源与时间提示，不建设独立文件历史。
3. AI 项目理解和基础概览：解释项目、版本差异，提供可追溯的摘要。
4. 模块 2 全景与信息汇总：从现有蓝图和开发记录展示模块/功能、设计与开发进展；丰富生成式可视化按需。
5. 模块 3 最小知识库及后续提醒：可独立推进，不要求严格等待模块 2 完成。
