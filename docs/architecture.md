# Architecture

## 目标、状态与约束

本文件记录经 Human 确认的 v0.2 总体架构方向：在 v0.1 基线上调整为插件优先与双工作区协同。当前仓库已有 T01/T03 只读 MCP 原型；T02 已验证 DeepSeek Harness 复用 T01 工具，但完整模块 1 业务能力、模块 2 和模块 3 尚未实现。原型验证不等于产品模块验收。项目目标、阶段与证据见 [Project Brief](project-brief.md) 和 [README 当前验证入口](../README.md#当前验证入口)，功能分期见[产品蓝图](product-blueprint.md)。设计文件的 Git 版本、Human 决策与具体任务实施授权须分别识别；本文件本身不授权业务编码。

## 总体架构：本地优先的模块化单体核心，MCP 插件优先

- **本地优先**：核心业务逻辑及必要业务数据主要在用户本地运行、持久化；GitHub 与云端 AI 是按需访问的外部来源，不要求本地 Git 查询依赖云端在线。
- **模块化单体核心**：模块 1、2、3 保持清晰职责；业务接口独立于 MCP 协议、宿主客户端和未来 UI，初期不拆成微服务。
- **接入层与业务层分离**：T01/T03 已通过 MCP 向本地 Codex 提供受限只读工具并完成真实调用验证；T02 已验证 DeepSeek Harness 复用 T01 工具。T03 的 GitHub 基线工具尚未在 DSH 中验证；多个客户端复用同一套事实查询规则，不假定其工具能力或授权一致。
- **复用现有 AI 工具**：已有客户端负责聊天和 AI 推理；独立 Web/桌面工作台、统一聊天入口、自行集成模型和复杂全景 UI 均为后续可选形态，不是 T01 前提。
- **渐进实现**：已完成 Windows 本地 MCP 真实调用、Git 事实读取与 GitHub `main` 基线查询原型；下一步再添加必要的项目身份、持久化与版本变化感知，不预建同步系统、索引平台或 Agent 编排。
- **已验证的技术试行**：Python + MCP SDK + 系统 Git CLI，通过 Windows 本地 stdio 运行；T01/T03 已由 Codex 真实调用，DSH 仅验证了 T01 工具。暂不引入 FastAPI。SDK 升级、打包/安装、宿主权限边界和其他客户端的支持范围仍需按具体任务验证。

ChatGPT 云端规划空间与本地 Coding 工作区具有不同的数据可见性；不是同一个自动同步的文件系统。

## 模块职责和协作边界

### 模块 1：项目接入与上下文管理

- 独立接入**本地项目目录**和**GitHub 仓库**，或将两者显式关联到同一个稳定的逻辑项目；不假定本地与远程状态一致。
- 只读优先，按需浏览目录与文件、查询本地 Git 工作区状态、分支、提交及差异，获取 GitHub 上可访问的仓库信息与历史。
- **版本变化感知是近期核心能力**：在打开项目、主动刷新或后续受控周期检查时，取得当前版本事实，与上次成功观察到的必要标识进行比较；展示变化来源、相关版本和检查时间。同步失败须标识旧信息可能过期。
- 保存必要的项目来源引用、关联关系、最近成功检查的提交/分支标识与时间、连接状态；不默认复制代码仓库、不永久保存每次扫描结果或完整差异、不另建 Git 版本控制体系。
- 已提交的 Git 历史以源系统为准。本地未提交修改可即时查询，但没有独立快照就无法还原两次检查之间的所有编辑过程。
- 通过与传输无关的核心业务接口向 MCP 适配层及未来模块 2 提供带来源、版本与观察时间的事实；**不决定功能是否已完成，也不管理正式任务状态**。
- 多客户端普通查询不得悄然把用户的比较基线或“已查看位置”向前推进；最近成功观察版本、指定比较基线与用户已确认阅读位置应区分，具体存储规则在版本变化任务中确定。

### 模块 2：智能项目管理与项目全景

- 产品方向是让用户一眼理解项目的**目标、模块、功能、设计进展及开发进展**，而不是单纯统计任务数量。
- 首期以**只读项目概览和已有记录汇总**为主：优先复用产品蓝图、架构文档、仓库内 Markdown 任务与审核记录，以及按需查询的 GitHub Issues、PR 和相关验证证据。
- 功能结构以现有项目蓝图为主要来源，按需关联任务与证据；关联不明确时提示待确认，不凭文件夹结构或标题相似度强行合并。
- 区分设计成熟度、开发/验证成熟度及文档的 Git 版本；不因一次提交、PR 合并或测试通过就自动宣称功能已验收。
- Agent 继续按 [Workflow](../CONTRIBUTING.md) 负责开发、测试、自检和审核；模块 2 不重复实现测试/验收引擎、任务派发和第二套正式状态。Human 保留最终验收。
- AI 分析可以提出变化影响与进度建议，但须与原始状态和正式验收记录明确区分；优先复用现有 AI 客户端，完整独立可视化界面不作为首期前提。

### 模块 3：个人知识库

- 独立支持 PDF、技术文档、网页/视频链接、笔记的收藏、基础分类、检索和 AI 辅助总结；不以存在项目为前提。
- 用户正式导入的资料可以采用托管副本，现有外部文件及链接可采用引用模式；两者的删除、备份及失效规则不同。
- 与项目或任务的关联是可选能力；知识库不负责代码版本控制或项目正式验收。

### 共享核心、MCP 接入与可选工作空间

- **本地核心**管理项目身份、来源关联、必要存储和业务权限；各模块管理自身规则，不依赖具体 MCP 工具、聊天历史或 UI 组件。
- **MCP 适配层**负责受限工具、输入校验、访问授权、带来源的结构化结果和失败语义，不另建正式项目状态。不同本地客户端共享工具语义，但不自动共享聊天记忆、Agent 权限或本地文件的云端可见性。
- **云端规划空间**优先复用 GitHub 接入读取已合并设计、已推送任务分支与 PR/验证证据；需要成为正式项目成果的讨论决定遵循现有 Git/PR Workflow。
- **未来可选工作空间**可以提供项目首页、知识入口、全景图与 AI 对话；在现有宿主界面不能满足实际需求时再建设。
- 模块 2 可读取模块 1 的事实，但应能展示未关联仓库的规划项目；模块 3 保持独立。Agent 的任务、审核与 Human Merge Authority 继续遵循 [Workflow](../CONTRIBUTING.md)。

## 双工作区协同与事实边界

| 来源 | 可以验证的事实 | 不得据此推定 |
| --- | --- | --- |
| 本地 Coding（Codex、DeepSeek Harness） | 授权目录内实际文件、Git HEAD、工作区状态与可访问的远端信息 | 过期的 `origin/main` 等于实时 GitHub；不同 Agent 已自动同步 |
| GitHub 共同基线 | 已合并 `main`、已推送任务分支/PR 及实际附带的验证证据 | 本地没有未提交工作，或所有功能都已正式验收 |
| 云端规划（ChatGPT 项目空间） | 当前讨论以及实际查询过的 GitHub 项目版本和文件 | 聊天决定已自动写回 Git，或能直接读取本地未提交改动 |

- 每次结论保留实际来源、版本标识、观察时间及新鲜度；失败、过期与未知不得写成“无变化”。
- 设计批准、文档合并、开发授权、验证证据与 Human 验收是不同事件。
- 工作区交接按现有 [Workflow](../CONTRIBUTING.md) 在开工前核对远端和本地基线、交付时报告各来源可见状态；不重复实现 Git 同步，也不默认自动 pull/push。

## 数据归属与最小存储

| 类型 | 归属与处理 |
| --- | --- |
| 外部源数据 | 本地代码、远程 GitHub、网页等保留原始归属；默认引用和授权读取，不擅自移动/删除 |
| 应用业务数据 | 项目身份、来源关联、必要配置、用户笔记及确需持久化的记录保存在本地；正式状态以约定的权威记录为准 |
| 托管知识资料 | 用户主动导入的文件可由知识库管理副本，区别于外部引用文件 |
| 衍生数据 | 提取文本、AI 分析、搜索索引、缩略图与缓存应标识来源，能重建的尽量可重建；编辑后正式保存的用户知识不是可随意清除的缓存 |
| 凭证、日志与备份 | GitHub/模型密钥与普通业务数据分离，敏感备份受保护；外部源文件是否纳入备份须明确 |

应用运行数据与应用代码仓库分离。解除项目关联不删除原有代码；归档、解除关联、删除托管资料与清理缓存的语义应区分。迁移时允许重新绑定已移动的项目路径。完整备份、恢复及凭证存放技术尚待设计。

## 项目事实、AI 与可视化边界

1. **事实层**：Git、本地工作区、GitHub、项目文档及实际测试/审核记录提供可追溯信息；明确来源、版本、观察时间和可用性。
2. **AI 理解层**：根据当前目标按需读取最小必要上下文，解释项目结构及版本变化，辅助整理功能结构和可视化描述；其判断是建议，不是原始事实或批准。
3. **表现层**：基础项目概览、版本变化和来源详情必须稳定可用；功能卡片、关系图和丰富的 AI 生成效果图可渐进增强。静态效果图不能替代可交互详情或正式状态数据。

项目或网页内容为不可信数据，不能借内容文本授予工具权限。本地 MCP 工具必须限制授权目录、验证路径和参数、避免路径逃逸及任意命令执行；凭证不得混入工具输出、日志或仓库。云端模型调用限制发送范围；默认只读访问项目数据，文件写入、命令执行、Git 推送与正式状态改变需要独立授权。外部服务不可用时，本地已有数据和可查询事实应尽量可用，同时展示远端/AI 能力不可用或信息过期的限制。

## 尚未决定

- 在已测试的 Windows Codex 与 DSH 环境之外的客户端支持范围；SDK 升级、打包/安装、宿主权限和长期兼容策略。独立 Web/桌面界面及其框架仍待实际需求决定。
- 数据库/存储、模块接口、跨进程共享状态与用户比较基线语义、缓存/索引和增量检查细节。
- 本地/GitHub 权限模型、凭证管理、失败恢复、备份及数据迁移实现。
- AI 提供方、模型 API、生成式图像/结构化可视化方案、费用与隐私策略。
- 功能/任务映射规则、双维度状态的具体枚举、可靠进度统计定义，以及提醒触发机制。

重大决策遵循 [Workflow](../CONTRIBUTING.md) 的授权、验证和审核要求。当前仓库已有只读 MCP 接入原型，但尚无完整模块 1 业务能力，也无模块 2、模块 3 的实现证据；运行与验证现状见 [README](../README.md#当前验证入口)。
